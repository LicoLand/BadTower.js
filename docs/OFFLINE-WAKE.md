# Offline wake hook

**Status: design.** No wake code, configuration, binding, or test exists
in this repository. The rule below is the contract a future
implementation must satisfy.

## Problem

A packet can arrive while the recipient device is offline. The packet is
stored permanently, so nothing is lost; the recipient will receive it on
its next Claim or WebSocket connection. But a device that is asleep or
disconnected has no way to know it should reconnect. The operator may
want to send an external wake signal through a notification service the
device already uses.

The wake hook is **not** a delivery mechanism and **not** a Station
protocol feature. It is a best-effort hint that the mailbox has something
to collect. A lost wake changes only latency, never delivery: the packet
remains stored until Settle or Revocation.

## Privacy boundary

The wake signal must contain:

- no packet content, length, hash, or type;
- no mailbox id, delivery handle, subject, admission credential, or
  Station key;
- no sender identity, address, endpoint tag, or protocol metadata;
- no recipient identity, email address, phone number, or device name;
- no per-event unique identifier that lets the notification service
  correlate events across time;
- no timestamp finer than a coarse bucket.

The notification service learns only: "some mailbox on this Station has
something to collect, in this coarse time bucket, for this rotating wake
token." The operator's mapping from `wakeToken` to a device push channel
lives in the notification service, not in the Station.

## Signal fields

The Station sends one fixed-size binary body over HTTPS POST to the
configured wake endpoint. Fixed binary keeps the native contract's
opaque style and avoids JSON field drift.

| Field | Size | Value |
| --- | --- | --- |
| `version` | 1 | `1` |
| `event` | 1 | `1` = packet available |
| `wakeToken` | 32 | opaque per-mailbox token, provisioned out of band |
| `bucket` | 4 | coarse UTC time bucket, `u32` big-endian |
| `mac` | 32 | HMAC-SHA256 over `version ‖ event ‖ wakeToken ‖ bucket` |
| **Total** | **70** | |

- `wakeToken` is generated by the operator or endpoint and stored in the
  mailbox's private metadata. It must not be derived from the mailbox id,
  the subject, or the handle. Rotating it is an operator action; revoking
  the mailbox deletes it.
- `bucket` is the number of whole coarse intervals since the Unix epoch.
  The interval is an operator configuration (for example, one bucket per
  several minutes), not a protocol constant. A coarser bucket reduces
  timing correlation.
- `mac` uses a separate wake key, not the `btm1`/`btr1` Station key. The
  wake endpoint verifies it before acting. A failure is counted, not
  retried indefinitely.
- There is no mailbox id in the body. The notification service routes by
  `wakeToken`, which is opaque to the Station's routing layer.

## Trigger and coalescing

The hook may fire only when all of these are true:

1. a Submit was durably accepted;
2. the target mailbox has a configured `wakeToken`;
3. the target mailbox has no ready live socket at that moment;
4. no wake has already been sent for this mailbox in the current
   `bucket`.

The fourth rule coalesces a burst into at most one signal per bucket. It
requires a single mutable `lastWakeBucket` field, overwritten in place;
no wake history is stored. If the wake endpoint fails, the Station
increments an aggregate failure counter and does not retry in a loop.
The next bucket may try again.

The hook must not fire on Claim, Settle, Revocation, a rejected Submit, a
transient Submit, a health check, or a connection that is already live.

## Station behavior when not configured

**Unconfigured is the default and changes nothing.** If `wakeToken` is
absent, or the wake endpoint/key is not configured:

- no outbound request is made;
- no `lastWakeBucket` is written;
- no new storage row or schema is created;
- Submit, Claim, Settle, Reserve, Revocation, health, capacity and the
  native contract version behave exactly as they do today;
- a plugin or protocol listener sees no difference.

This is a hard requirement. The wake hook is an optional side channel,
not a dependency of the native contract or of any plugin.

## Configuration

The implementation should use operator configuration, not protocol
fields:

| Name | Purpose |
| --- | --- |
| `BADTOWER_WAKE_URL` | HTTPS endpoint that receives the signal |
| `BADTOWER_WAKE_KEY` | 32-byte base64url HMAC key for `mac` |
| `BADTOWER_WAKE_BUCKET_SECONDS` | coarse bucket width |
| per-mailbox `wakeToken` | opaque routing token, provisioned out of band |

The key is a secret and follows the same private-material rules as the
Station key. It is never placed in a tracked file, argv, or log.

## Delivery and failure semantics

- The signal is best effort. A timeout, non-2xx response, DNS failure, or
  TLS failure is an aggregate failure, never a Submit failure. The packet
  is already durable; the wake is only a hint.
- The Station does not wait for the wake endpoint before answering the
  Submit. The response is the same `accepted` it would return without a
  hook.
- The Station does not treat a 2xx from the notification service as
  delivery, receipt, or user acknowledgement. It is a Station signal and
  remains untrusted.
- There is no retry queue, no alarm, and no background loop. A failed
  wake is not persisted as a per-mailbox record.

## Cost and abuse notes

- The outbound request is a Worker subrequest; Cloudflare does not bill
  Worker subrequests as requests, but the operator's notification service
  may charge. The wake path must stay off the hot path of every Submit.
- Coalescing bounds the signal rate per mailbox to one per bucket. A
  sender who knows a mailbox id can still cause one signal per bucket by
  submitting repeatedly; that is a notification-service cost, not a
  content leak.
- The wake endpoint must not be an open reflector: it verifies `mac`,
  enforces its own rate limit, and never echoes the body.
- The signal is small and fixed-size, so it adds no meaningful Worker CPU
  or DO duration. It must not keep the Durable Object active: send it
  after the durable write, without awaiting it on the response path, and
  do not create pending I/O that pins the object.

## Implementation tasks

The configuration, per-mailbox token, coalescing field, signer, sender,
and tests are registered as a follow-up Kanban task. No part of this
design is claimed as implemented.

## Non-goals

- No content, identity, address, or mailbox id leaves the Station.
- No guarantee of wake delivery, ordering, or latency.
- No per-event history, no wake log, no per-mailbox delivery receipt.
- No change to the native contract, the LicoArc listener, or any plugin
  when the hook is unconfigured.
